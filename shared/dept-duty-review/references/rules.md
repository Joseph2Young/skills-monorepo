# 固定规则（写死，每次生效，不每次确认）

## 一、审核原则（三条，沿用）

1. **消失部门**：职能必须有人接盘（由新设部门或原有部门承接）。旧职能以比对表的「调整前职责」列为准。
2. **新设部门**：职能必须从老部门剥离，严禁凭空新增。基准文件里有表述的按基准文件为准。
3. **扯皮事项**：一项职能由业务部门与科技/中后台共同承担时，业务部门考核权超过 60% 的归业务部门；科技部门只评价技术建设，业务部门评价需求满足度。

## 二、颗粒度规范

1. **主要职能**写「管什么」——定位、归口（牵头）范围、覆盖边界、主要管理对象。一段话，不罗列具体工作事项。
2. **具体职责**写「做什么」——一事一条，每条以「负责／牵头／组织／拟定／审核／督导／承办／完成」等动词起首，单条 30～80 字。
3. **颗粒度对齐**：同一部门内各条职责颗粒度相当，同类事项合并，避免「一条只写一句话」或「一条涵盖多个不相关事项」。
4. **不写工具与手段**：系统、平台、模型、数据集市、系统群等实现手段不作为职责；职责只表述管理事项、管理动作、管理结果。
5. 职责条数一般 6～15 条。

## 三、颜色约定（固定）

| 标记 | 颜色（ARGB） | 说明 |
|---|---|---|
| 删除 | 深绿 `FF006400` + 字体上横线 | 基准原文被删，保留原位加横线，便于逐字比对 |
| 新增 | 深绿 `FF006400`（不加线） | 本次新增或部门整体调整新增 |
| 修改 | 深蓝 `FF0000FF`（不加线） | 基准原文被改写后的内容 |
| 冲突 | 品红 `FFFF00FF`（不加线） | 资料与表内冲突点，以「【冲突】」起首说明 |
| 交叉重叠 | 橙 `FFFF6600` | 部门间职能交叉，独立表/列展示，标【重】【交】 |
| 未改动 | 黑 `FF000000` | 存量未动 |

**留痕口径**：
- 整条被合并、替换或删除的原条目，置于本部门「具体职责」列末段，前加一行「【留痕】以下为本次修订中被合并、替换或删除的原表条目，原文保留并加删除线，供逐条比对」，其后逐条整条划删。
- 条目对齐须先做全局最优匹配（见 trace-tech.md），不复用逐行 diff。

## 四、效力顺序

基准文件（请示）＞ 部门比对表 ＞ 过程材料。三者冲突，一律以请示为准；部门之间拟移交事项，依据请示并结合过程材料确定。
